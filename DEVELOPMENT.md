# Development notes

## Architecture decisions

- `/dungeon enter` queues non-presentation `DungeonGenerationJob`s in `DungeonInstanceManager`; its named, weighted-random, and lifecycle variants no longer call the synchronous creation loop. `GenerationTickBudget` accounts for elapsed generation work across both command entries and catalyst jobs in one server tick, including failing or over-budget chunks. Return capture and teleport happen only after normal finalization creates the platform and bound portal. Pending entries retain the requesting player session and source dimension; duplicate requests are rejected, unavailable or moved players cancel through guarded instance cleanup, and unfinished shutdown records use existing conservative `CREATING` recovery. Legacy synchronous Java creation methods and `/dungeon create` remain unchanged.
- `DungeonGenerationLevel` supplies a bounded `WorldGenLevel` over the already-live instance chunks. Generated structures, entrance construction, terrain cleanup and return portals write through `LevelChunk#setBlockState` and retain `markAndNotifyBlock`; ordinary `Level#setBlock` remains untouched. This avoids premature gameplay-protection rejection when a placed block entity activates a protected region before later chunks are generated. Chunk lighting, heightmaps, block entities and persistence stay on the real chunk path.
- For flat-sampled grounded structures with measured template foundations, the terrain surface is capped at the adaptation-aware authored foundation reference rather than waiting until the entire roof would be buried. Unknown procedural geometry retains the previous conservative seating fallback; ocean, underwater, floating and underground environments are unaffected by this cap.
- Runtime levels use vanilla `ServerLevel`, `ServerChunkCache`, `LevelStem`, and the active save's `LevelStorageAccess`. A single mixin accessor exposes Minecraft's private runtime level map and storage handle; no reflection or internal access is spread through the lifecycle code.
- Instance level keys are `instancednotinfinite:instances/<32 lowercase UUID hex characters>`. Minecraft therefore stores them below `world/dimensions/instancednotinfinite/instances/<uuid>`.
- A marker file containing the mod ID, canonical UUID, and schema version is mandatory before deletion. Cleanup also proves that the normalized path is exactly one UUID child of the dedicated root.
- Resolved definitions, selected biome, structure kind, seed, bounds, origin, retained terrain-surface height, entry position, and automatic entry yaw are snapshotted in overworld `SavedData`. Reloads affect new instances only.
- Player return locations use separate overworld `SavedData`; they survive deletion of an instance level.
- Version 1.1 refines automatic environment hints from actual flat-sample placement, not a structure-type whitelist. New aquatic plans persist `OceanFloorY` separately from their waterline; older saved plans without that field retain their previous terrain model. Floating candidates are checked again after `postProcess` so deferred ground projection does not trigger terrain removal.
- Fully submerged automatic structures first try their authored dry spaces; when none exists, the normal approach builder creates a dry platform at the retained water surface without carving or moving the underwater structure.
- Floating construction temporarily writes a flat biome palette and suppresses decoration. A scoped `LevelChunk#setBlockState` capture records authored writes before same-state short-circuiting; chunk-budgeted cleanup preserves those positions and their block entities. Persisted `FloatingVoid` keeps lazy and restored chunks empty. Surface landing selection requires nine supported, dry, sky-visible cells and prefers the nearest edge. Route selection checks the instance footprint and build height, not existing obstructions; the builder carves configured headroom through walls along the minimum-three-block-wide bridge while preserving supported authored floors.
- Player pre/post tick guards return only players below an instance dimension's minimum build Y. The existing persisted entrance return location supplies the original dimension and portal exit offset; void rescue clears fall distance/velocity and sets a portal cooldown. Missing return records use the configured safe fallback.
- Standard instance environments retain `NoiseBasedChunkGenerator` only as the structure-API-compatible wrapper around a `FixedBiomeSource`. The generator writes deterministic finite strategy blocks directly and skips vanilla density, surface, carver, feature, and worldgen-creature passes. Smooth value noise shapes heights, while a separately salted three-dimensional high-frequency coverage mask dithers the tapered outer band horizontally and vertically into guaranteed void. `CUSTOM` definitions continue to resolve their registered strategy through the same bounded fill path.
- `DungeonChunkGenerator#createStructures` is an unconditional no-op. Automatic catalogue entries are placed explicitly from their retained start, so ordinary structure sets cannot add unrelated structures to an instance.
- Environment behavior uses strategy objects rather than one generator switch. `CUSTOM` strategies can be registered through the public API before instance creation.
- Automatic discovery expands configured structure tags once per catalogue rebuild, retains each tag's resolved member list for named pool catalysts, resolves static registry metadata without generating layouts, and snapshots a full definition only when an instance is created. Pool-only tags suppress exact catalysts unless a member is directly configured. Advanced datapack definitions shadow automatic options with the same ID.
- Presentation is trigger-independent. The catalyst, commands, and public API all create the same persistent `DungeonManifestation`; there is no ritual or quest-mod dependency in the core.
- Manifestation generation reuses the exact retained layout and terrain plan but advances through chunk-sized server-thread work units. Elapsed time is the primary global tick budget and the operation count is a secondary cap. The animation clock remains at zero through terrain/heightmap preparation and begins when the first non-empty structure batch is captured; client scoring uses the planned structure bounds and calibrates that first batch's minimum score to zero. Until that batch arrives, a synchronized client-only dust cue marks the future portal volume using configurable color, rate, size, radius, and `RING`/`SPIRAL`/`CONVERGING` motion, adding no server particle traffic. Direct legacy creation remains synchronous for API compatibility.
- `DungeonVisualSnapshot` records the selected structure's retained surface shell without terrain. Each structure chunk is compared with its controlled pre-placement block state across the complete build height, which also catches vanilla pieces such as igloos that shift vertically during post-processing. Portal appearance does not inspect that block stream: automatic layer RGB comes directly from the resolved biome's fog color. The server-side snapshot is streamed in bounded batches and remains transient across restarts. Once an exact icon completes, the client persists a palette-compressed copy of its structure blocks under a save-specific UUID and reconstructs only the miniature source on later connections. Client fitting uses the shell's tight occupied bounds, so both presentations are centered and scale-normalized to the actual structure.
- Hologram revisions are compiled on the render thread under a 4 ms/2,048-block per-tick budget. Six-neighbor occlusion removes hidden directional faces, baked-model quads are grouped into 64 deterministic reveal buckets, and each non-empty bucket is uploaded once to a static vertex buffer. Rendering then performs only bounded GPU draws; it does not sort blocks, query baked models, or rebuild vertices per frame. The previous complete revision stays usable while streaming builds its replacement. Animated entity-block models use a capped fallback, and logout/resource reload/removal close every owned GPU buffer.
- Portal placement is generation-gated. A distinct non-enterable opening state grows the colored plane/volume from the hologram collapse point. Per layer, an advanced datapack `#RRGGBBAA` override wins; otherwise enabled biome-fog derivation applies configured opacity and then falls back to the global hex value. The resolved pair persists on the instance and manifestation and is shared by source and destination endpoints. Portal yaw persists and synchronizes as a normalized integer, so rendering, interaction bounds, targeting, and outward return placement support non-cardinal angles. Paired inner/outer dither fragments use a dedicated spawn phase: they fade from a small inward offset onto the current edge before their original outward, shrinking animation begins. The countdown contracts the solid surface from the top and both sides, holds the bottom fixed, and floors its dimensions at the configured minimum; `CLOSING` then turns the remaining paired cells into deterministic particles that travel radially, upward, and normal to the portal while shrinking. Optional Jade integration owns loading and portal information by default when installed, including synthetic ray targets for the client-only hologram/source portal; otherwise an independently enabled built-in panel shows the same target content. Entry resolves the portal's persisted manifestation UUID to one exact active/vacant instance; the instance-side endpoint stores that exact instance UUID and returns players to a configurable outward offset on their original approach side.
- The resolved server catalogue, stable per-dungeon portal preview colors, and named structure-pool membership are synchronized to clients. Preview colors use the real explicit override, deterministic weighted biome selection, opacity, and global fallback resolver; pool-only members receive previews without becoming exact catalysts. Optional JEI and EMI plugins expose component-distinct exact and pool catalysts and rebuild their indexes after catalogue changes. Pool GUI icons crossfade among completed member sprites; held/dropped items prefer completed 3D miniatures and fall back to portal cubes whose particles emit across all six faces.
- Interrupted non-open manifestations fail conservatively and hand their instance to the existing guarded cleanup lifecycle. Consumption policy and refund completion persist separately so recovery cannot duplicate or silently lose a catalyst.

- If a generated start lies too near a build-height edge, every piece is translated together before the retained start is rebuilt and measured. This preserves the full requested vertical padding and falloff instead of clipping the guaranteed region.

## Compatibility and limitations

- `DIRECT` supports worldgen structures and NBT structure templates. `NATURAL` uses a worldgen structure's own generation-point and piece logic, but arbitrary third-party structures can still reject the constrained generator.
- A worldgen structure whose start cannot be produced fails cleanly before players teleport. Template placement is generally more predictable.
- `NONE` skips biome decoration. `SAFE` runs vegetation and top-layer stages; `FULL` runs the full placed-feature pass. Floating instances suppress decoration on disposable terrain; unrelated structure sets remain disabled separately.
- Standard environments preserve the selected biome's identity and use biome-category material palettes with controlled flat/finite geometry, not vanilla surface rules or density terrain.
- Structure DATA/jigsaw marker extraction is not yet generic. Automatic surface-like entries instead inspect placed door/gate orientation and walkable boundary openings; explicit relative entry coordinates remain supported for advanced definitions.
- Runtime dimension registration is version-sensitive. The backend is isolated so a future NeoForge public service or vetted library can replace it.
- DynamicDimensions 0.9.1 was evaluated after the built-in backend passed its lifecycle gate. Its `minecraft/1.21` branch targets Minecraft 1.21.1/NeoForge 21.1 and is MIT licensed, but create/load/unload/delete can register one tick later and the library intentionally leaves restart tracking to consumers. Retaining the now-tested backend avoids a required runtime dependency; `DynamicLevelBackend` remains the adapter seam.
- Distant Horizons 3.2.0-b retains a SQLite WAL handle after dynamically unloaded levels even after its unload callback reports the level closed. Optional mixins prevent DH's server level, chunk, and dimension-change handlers from attaching only to `instancednotinfinite:instances/*`. Client mixins suppress all four LOD/fade render entries, the DH fog override, end-of-level framebuffer bookkeeping, and real-time block updates while the active level is temporary. Ordinary dimensions and player login/logout tracking retain normal DH behavior, no global DH config value is changed, and the compatibility classes are not applied when DH is absent.

The API-compatible generator now writes the existing environment strategies directly, uses interpolated multi-scale height noise instead of stepped hash noise, tapers grounded terrain thickness through the outer band, and applies deterministic two- or three-dimensional dithering whose coverage falls smoothly from solid padding to guaranteed void. Structure seating once again moves controlled terrain to the authored foundation rather than translating a valid structure to meet an unrelated vanilla surface. The selected biome remains real for identity, colors, weather, mechanics, and spawning, but density terrain, surface rules, carvers, biome features, and worldgen creature passes are skipped. All 86 unit tests and 14 required GameTests pass; the final 0.4.2 lifecycle suite completed in 9.904 seconds, retained 114 hologram blocks from a 113-block manifested igloo change set, resolved sampled/fallback portal colors, and deleted every temporary level live.
- Version 0.4.3 makes surface-like terrain edges dissolve per voxel in X, Y, and Z instead of retaining dithered whole columns, while leaving the guaranteed support region solid. Automatic portal colors ignore gray and near-black map colors, select the dominant sampled chromatic hue, and enforce a readable saturation before applying each layer's configured opacity. Catalyst GUI contexts use the generated isometric 2D sprite; held, dropped, framed, and other world contexts use the upright 3D miniature. Source and destination portals show that cached miniature beneath the portal surface only when the camera ray intersects the front of the rendered opening, with the destination endpoint persisting its dungeon ID for reload-safe lookup. All 90 unit tests and 14 required GameTests pass; the final lifecycle suite completed in 7.871 seconds, sampled 12 chromatic candidates from 329 manifested igloo changes, retained 331 hologram blocks, carried matching portal appearance and dungeon identity to the return endpoint, and deleted every temporary level live.
- Version 0.5 adds ordinary recipe-manager recipes for targeted catalysts with explicit-datapack precedence, per-dungeon role/tier overrides, bounded template/jigsaw palette analysis, biome/environment/name inference, relative rarity/size scoring, deterministic tag ingredients, datapack-defined cost tiers, reload-safe profile caches, and `/dungeon recipe explain`. All 119 unit tests and 16 required GameTests passed, and a dedicated reload retained the same palette-derived igloo recipe before and after `/reload`.
- Version 0.6 adds named structure-tag pool catalysts, pool-only member suppression with direct-ID exceptions, world-seed-stable nine-slot member recipe mixing, exact/block-tag ingredient denylists, exact/structure-tag automatic-recipe denylists, and client-synchronized pool visuals. Pool icons crossfade as member sprites become available; in-world items shrink, swap, expand, and rotate only through completed 3D miniatures. All 123 unit tests and 17 required GameTests pass. A dedicated server retained two members, one pool-only member, two exact generated recipes, and one pool recipe across `/reload`, applied the configured snow-block/log exclusions, and stopped cleanly through RCON.
- Version 0.6.1 makes the interval between structure-pool catalyst icon changes and 3D miniature changes configurable from 1 to 3600 seconds, with a five-second default. Crossfading and shrink/swap/expand timing retain their existing animation shapes inside the configured interval. All 124 unit tests and 17 required GameTests pass.
- Version 0.7 adds optional Jade-first loading/portal information with an independently enabled built-in fallback, replaces in-world catalyst miniatures with small square portals whose server-synchronized preview colors use the real dungeon portal resolver, and gives every recurring edge fragment an inward-to-edge fade-in before its prior animation. All 126 unit tests and 17 required GameTests pass. A no-Jade dedicated server reached `Done`, exposed RCON, saved every dimension, and stopped cleanly; a Jade 15.10.5 client discovered and loaded the optional plugin without registration or classloading errors.
- Version 0.7.1 restores completed 3D dungeon miniatures as the preferred held, dropped, framed, and other in-world catalyst render. When no suitable exact or pool-member miniature is ready, the resolved-color fallback is an equal-sided portal cube whose eased dither emits from all six faces; unbound catalysts use that fallback permanently because they have no singular miniature. Jade targeting follows the complete rendered portal volumes for every loaded endpoint rather than requiring the anchor block, and the loading panel targets both the initial particle volume and a padded animated miniature volume.
- Version 0.7.2 makes every portal dither fragment a true cube and reduces the complete held/dropped fallback portal effect, including its six-face particle field, to one quarter of its previous scale.
- Version 0.7.3 makes the mod's own rendered-effect ray trace authoritative for Jade. An optional Jade-only mixin inserts the selected portal, preparation-particle, or hologram hit before Jade's null-target early exit; the normal Jade accessor and component pipeline then displays the bridged target without requiring a floor or anchor-block hit.
- Version 0.8 adds depth-aware portal contraction with matching full/minimum depth defaults; biome-derived inner portal colors with configurable transparency and black-to-white relative shading; biome-category surface materials and bounded safe surface decoration; fully solid underground encasement with deterministic-random walkable authored-piece entries, configurable bridge/platform clearances, and an intentional stone route; persistent per-item and per-command initial/post-visit/forced lifecycle overrides with `-1` infinite semantics; and permission-level-2 gating for the complete `/dungeon` tree.
- Version 0.8.1 avoids re-encoding registered structure placements while inferring portal-recipe rarity. Frequency and exclusion-zone metadata now come from the matching structure-set datapack JSON, so custom placements such as `integrated_api:stronghold` are supported even when their NeoForge registration wrapper cannot be cast during codec serialization. The `strongholds` generation step now infers `UNDERGROUND`, and constant uniform absolute start heights such as Integrated Stronghold's Y=15 are retained, routing the structure through solid encasement and the intentional underground entry approach instead of surface handling. All 136 unit tests and 19 required GameTests pass. A dedicated server completed `/dungeon reload`, rebuilt all fixture catalogue entries and recipes, saved every dimension, and stopped cleanly through RCON.
- Version 1.0 adds an exact-item-or-`#item_tag` portal completion offering, defaulting to blaze powder and consuming one item only after the bound active/vacant instance completes. Both open endpoint types use their persisted exact instance identity and the full rendered interaction volume. The supplied mod icon PNG replaces the mod-list logo and every not-yet-generated 2D item placeholder without byte changes; the established animated portal cube remains the fallback in held, dropped, framed, and other non-GUI contexts. Structure-pool animation now retains stable member slots while caches populate and uses a continuous swap rotation, removing both index remapping and the full-scale 180-degree interval jump. All 140 unit tests and 19 required GameTests pass; the lifecycle GameTest throws a two-item blaze-powder stack through the rendered portal area outside its anchor, observes exact-instance completion, and verifies that one item remains. A dedicated server emitted the blaze-powder default, completed `/dungeon reload`, saved every dimension, and stopped cleanly through RCON.
- Version 1.0.1 persists generated portal-recipe structure profiles in deterministic, pack-shippable files under `config/instancednotinfinite/generated-recipes/`. Portable fingerprints cover the selected dungeon structures, inference configuration, template discovery, structure-set placement inputs, and exact analyzed structure/template resources; cache hits skip NBT palette analysis while recipes and reports are reconstructed against current datapack recipes, tiers, item tags, exclusions, pools, and world seed. Initial recipe installation waits for the loaded world config and template manager instead of analyzing twice during startup. `recipes.regenerateRecipeCache` forces one atomic rebuild and resets itself only after the cache is saved successfully. All 143 unit tests and 19 required GameTests pass; restart logs loaded the persistent cache and explicitly skipped structure-template scanning, while a forced-regeneration run rebuilt the same fingerprint and wrote the TOML flag back to `false`.
- Version 1.0.2 uses the existing biome-colored portal cube for inventory and recipe-viewer placeholders until a generated sprite is available. Structure-pool GUI slots preserve their member-specific colors and crossfade opacity while missing sprites populate; generated sprites still take priority. The non-GUI renderer, shared portal geometry, miniature renderer, and item-model transforms remain unchanged. All 145 unit tests and 19 required dedicated-server GameTests pass, including alpha-preservation coverage for placeholder crossfades. In-client visual confirmation remains outstanding.
- Version 1.0.3 recognizes Awesome Dungeon Ocean's sea-level-anchored boat structure types without adding a mod dependency or guessing from structure names. The official [3.3.0 NeoForge 1.21.1 JAR](https://www.curseforge.com/minecraft/mc-mods/awesome-dungeon-edition-ocean-neoforge/files/7033605) encodes `start_height.absolute=0`, but `AwsOceanBoatStructure` starts at the generator's sea level minus an authored hull offset (five blocks for the large frigate). Ocean inference now selects `OCEAN_SURFACE` for those types, and vertical fitting carries sea level through rather than inheriting the temporary Y=127 waterline. All 152 unit tests and 19 base GameTests pass. With that official mod and Library Ferret 4.0.0 installed only in the isolated GameTest run, all 20 required tests passed; the real large frigate was created, deleted, and recreated with bounds Y=57..124, waterline Y=63, and a dry arrival at Y=64. The real ocean-cage ruin remained `UNDERWATER`, and an explicit underwater override still won for the frigate. The optional `OceanBoatGameTests` fixture is excluded from the production JAR and registers only when the ocean mod is present. That run also logged invalid block-attached-entity positions while placing the mod's templates; decorative entity placement was not changed by this waterline fix. No client visual check was performed. Existing instances retain their saved terrain and require a fresh instance to use the corrected waterline.
